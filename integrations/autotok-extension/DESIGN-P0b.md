## 2. Signing: what must come from the page, and how

- Steps 1-7 need no TikTok signature (the Python `requests` path does them unsigned, uploader.py:328-361). Only step 8 is signed.
- Python has two ways: (a) `Signer` (signer.py) runs TikTok's obfuscated `signer.js/webmssdk.js/xbogus.js` in a stub page to compute `_signature`, `X-Bogus`, `msToken` -- but `requests`-signed publishes were rejected on 26/10 (`status_code` 5) and are now only a fallback (uploader.py:405-415, 640-660); (b) `browser_publish.py` (the mechanism that works): it never computes signatures. It waits until the SDK has wrapped `XMLHttpRequest.prototype.open/send` (`_SDK_READY`, lines 36-41, 60-62), then does `new XMLHttpRequest(); open('POST', url); withCredentials=true; setRequestHeader('content-type','application/json'); send(body)` (lines 44-57). The SDK's hooks add the signing params/headers (module docstring, lines 1-9).
- Therefore the extension does exactly (b), in MAIN world, in the real Studio tab. It is the same mechanism and no signer needs to be extracted. Wait condition: `document.readyState==='complete'` and `XMLHttpRequest.prototype.send.toString()` not `[native code]`. CAUTION: our own `hook-main.js` also replaces `send/open` at document_start, so the `[native code]` test is no longer valid for readiness; use a different SDK-ready signal (e.g. `window.byted_acrawler` / `window.generateBogus` as in signer.py:34-37, or compare against our wrapper identity), to be determined in the live run.
- Our hook sits below the SDK wrapper (installed earlier), so the SDK signs first and our `send` sees the signed URL: intercept mode can read the final URL+body and drop it. Whether the SDK also wraps `fetch` is unknown, hence XHR (as proven).
- tz_name: use `Intl.DateTimeFormat().resolvedOptions().timeZone` (Python: `local_tz_name`, uploader.py:104-128).

## 3. Video bytes to MAIN world
SW (Range fetch from the dev server, 1 MiB) -> content script (ISOLATED, as now). New: content script posts each chunk to MAIN with `window.postMessage({__autotok:1, kind:'chunk', nonce, index, buf}, origin, [buf])` (transferable ArrayBuffer, no copy). MAIN keeps `parts[]`. Alternative: content script builds a `Blob` and `URL.createObjectURL`, MAIN `fetch(blobUrl)` (blob URLs are origin-scoped and readable across worlds): simpler, one message, and `blob.slice()` gives the 5 MiB parts lazily. Recommended: Blob URL.
Memory for ~70 MB: base64 chunk transport already costs ~1.4x per chunk transiently; the assembled Blob is ~70 MB (Chrome may spill Blobs to disk); no second full copy in MAIN with `slice()`. Peak ~ video size + one 5 MiB part + CRC buffer. Measure `performance.memory` as today.
CRC32 needs each part's bytes: compute per slice just before sending (`await slice.arrayBuffer()`), do not retain.

## 4. Modes (X1 state machine unchanged)
- **selftest:** steps 1-6 only (create project, auth, apply, chunks, finish, commit). Report `video_id`, `creation_id`, size, timings, per-step HTTP status, sanitized response shapes. Never step 8; the dev server never authorizes selftest. Open question: does an uploaded-but-unposted video create a visible draft/side effect? Python never leaves one by design (project created, video committed, no post); unknown for the Studio "draft" list -> owner checks the account's Drafts and Studio "Posts" after the first run. Add a `--no-create` variant to separate the effect of step 1 vs. upload.
- **intercept:** selftest + build the full body (steps 7, body, schedule_time, options) and report it sanitized (omit `creation_id/video_id` values? keep ids, they are not secrets; drop any cookie/token fields). No step 8 send. Optionally also pass it through the SDK wrapper with our hook in `block` mode to learn which signing params the SDK adds (URL query names only, values redacted).
- **post:** `/api/authorize` (one-time, persisted before) -> single XHR for step 8. Never retried by the extension. Any error after the XHR `send` call = `uncertain` (as `PublishUncertainError`, uploader.py:664-698), except `_BrowserNotStarted` equivalents (SDK never ready) = definite, nothing sent.
- Authorization timing: upload (steps 1-6) happens BEFORE authorization (it creates no post); authorization is requested right before the post XHR, after the identity check (X3) -- same as today's `postStage`.

## 5. Result mapping (mirrors `_check_publish`, uploader.py:664-698)
HTTP !=200: 5xx/408/429 -> `uncertain`; other -> `rejected` (definite). Non-JSON -> `uncertain`. `status_code` not an int -> `uncertain`. `status_code != 0` -> `rejected` with `status_code/status_msg` (e.g. 5 = bad signing; schedule errors). `status_code == 0` -> `posted`; `item_id` from top level, `data`, or `single_post_resp_list[*]` keys `item_id/aweme_id` (uploader.py:146-193; never guess); keep `creation_id`, `video_id`, sanitized response (<= 8 KiB, secret-key filter as `sanitize_response`). Scheduled: report the `schedule_time` actually sent (UTC).

## 6. Risks / unverifiable until the real run
1. Page-origin CORS for `UploadHost` and for the cookie-less `finish`: the web client does it from Studio, so likely allowed; unverified.
2. SigV4 correctness in JS (canonical header set, `x-amz-security-token`, URL-encoding): easy to get wrong; verify with a unit test against Python's `AWSSigV4` output for a fixed key/date.
3. Does the SDK sign XHRs opened by our code the same way as Studio's? (Python proves it for a Playwright-driven page; the extension page is the real one, so expected.) Failure shows as `status_code != 0`/5 -> definite reject, nothing posted.
4. Bot detection: no UI events fired; fetch/XHR timing is machine-like; same fingerprint as the owner's real browser. Moderate risk; unknowable.
5. Size/time: 70 MB = 14 parts; each part 120 s timeout as Python; retry a failed part up to 3 times with the SAME `partNumber/uploadID` (idempotent per part); if `finish`/`commit` fails, restart the whole transfer with a new `uploadID`. No retry for step 8.
6. Background throttling in a minimized window: network fetches are not throttled like timers, but CPU for CRC32 of 5 MiB slices may be slowed; measure.
7. Draft/side effects of selftest (see 4); account-level rate limits on `create project`.
8. SDK-ready detection conflicts with our hook (see 2).
